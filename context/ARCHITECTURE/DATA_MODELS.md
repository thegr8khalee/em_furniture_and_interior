# Data Models

> The data model is PostgreSQL. [`docs/SCHEMA.md`](../../docs/SCHEMA.md) is the
> authority: it carries every table, every constraint, and the reasoning behind
> each one, written as the migration went. This page is the map — what exists,
> and where to look.
>
> The migrations in `apps/api/src/db/migrations/` are the schema itself. There
> are no ORM model files: the services write SQL, and a migration is the only
> thing that changes a table.

---

## The shape of it

Forty-two tables, in seven groups. The numbering follows the migrations, so
`0004_commerce.sql` is where the commerce tables are defined.

### Identity — `0002`

| Table | What it holds |
|-------|---------------|
| `customers` | Shoppers. Nullable `password_hash` and `supabase_user_id`, and a check that at least one is present |
| `staff` | Operators: role, explicit permission grants, active flag |
| `guest_sessions` | A shopping session before anyone has signed up |

### Catalog — `0003`

| Table | What it holds |
|-------|---------------|
| `sellable_items` | Anything that can go in a cart: name, price, promo price, **cost price** |
| `products` | The product half — category, SKU, warehouse location, lead times, SEO |
| `collections` | The collection half — a cover image |
| `collection_products` | Membership, ordered, one collection per product |
| `sellable_images` | Images, ordered, for either kind |

A product and a collection share `sellable_items` because an order line, a cart
line and a review all point at "something sellable" without caring which it is.

### Commerce — `0004`

| Table | What it holds |
|-------|---------------|
| `carts`, `cart_items` | One cart per customer or guest, never both, never neither |
| `wishlist_items` | Same rule, no header row needed |
| `orders`, `order_items` | Priced and numbered at placement; the item's name and price are copied onto the line |
| `order_status_events` | Every status change, with who and when |
| `payment_transactions` | Gateway charges and receipts recorded by hand |
| `coupons` | Discounts, with their own usage limits |
| `reviews` | Against a sellable item, one per customer |

### Inventory — `0005`

| Table | What it holds |
|-------|---------------|
| `stock_movements` | **The log.** Append-only, signed quantities, a reason on every row |
| `product_stock` | A cache the database maintains — never written by hand |
| `stock_reservations` | What is held for a confirmed order |
| `product_availability` | A view: on hand, reserved, available, low |

There is no quantity column to set. Every balance is derived from the movement
log, which is why an inventory discrepancy can always be explained.

### The ledger — `0006`, `0010`, `0012`, `0013`

| Table | What it holds |
|-------|---------------|
| `accounts` | The chart of accounts, thirty of them, with a postable flag |
| `journal_entries`, `journal_lines` | Double entry. Append-only, balanced by a trigger, numbered without gaps |
| `accounting_periods` | A month at a time, open or closed; a posting into a closed one is refused |
| `counters` | Gapless document numbers — orders, entries, expenses, purchase orders |
| `vendors` | Suppliers |
| `expenses` | Money spent: draft, approved, paid or void |
| `purchase_orders`, `purchase_order_items` | An intention to buy, which becomes stock and a debt on receipt |

### Content and engagement — `0011`

`blog_posts`, `faqs`, `projects`, `project_images`, `designers`,
`consultation_requests`, `consultation_room_photos`, `promo_banners`,
`flash_sales`, `flash_sale_items`, `notifications`, `loyalty_transactions`,
`audit_logs`, `activity_logs`.

### Housekeeping

`schema_migrations` records what has been applied, with a checksum, so an edited
migration is a loud failure rather than a silent divergence.

## What is worth knowing before writing a query

- **Money is an integer of minor units** (kobo) in every column, and naira on
  the wire. `apps/api/src/lib/money.js` is the only place that converts.
- **Ids are UUIDs**, generated by the database.
- **A cost price is not public.** `sellable_items.cost_price` is read by the
  posting rules and published only on admin routes: beside a selling price it is
  the margin.
- **History is append-only** in two places — `stock_movements` and the journal —
  and both have triggers that refuse an update or a delete. A mistake is
  corrected by recording its opposite, which leaves both visible.
- **Constraints carry the rules.** A cart with two owners, an order with no
  buyer, an expense whose total does not equal net plus tax, a paid expense with
  no date: each is refused by the schema rather than by a handler that might be
  bypassed.

## Where the old model went

The system was twenty Mongoose collections until August 2026. The rewrite of
each one, the rules that turned out to be implicit, and the bugs that surfaced
while moving are all in [`docs/SCHEMA.md`](../../docs/SCHEMA.md) — including the
ones worth knowing about: a cart that existed twice, loyalty points that could
not be explained from their own history, and a flash sale whose targeting
stopped resolving when the catalog moved.
